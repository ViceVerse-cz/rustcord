# On-demand user profiles

Implemented September 10, 2026. Clicking an existing visible user requests one profile through the authenticated Discord adapter. Closing or replacing the card cancels its task. The reducer accepts only the current user/guild/request/session combination, retains one result in RAM, and clears it on logout, reconnect/permission invalidation, or session failure. It does not enumerate profiles, fetch mutual friends, read private notes, or persist profile metadata.

The request is `GET /users/{user_id}/profile` with `with_mutual_guilds=true`, `with_mutual_friends=false`, `with_mutual_friends_count=false`, and an optional existing `guild_id` from the open conversation, independent of the server currently browsed in the sidebar. This normal-user route is **unofficial**, evidenced by [discord.py-self's HTTP implementation](https://github.com/dolfies/discord.py-self/blob/master/discord/http.py#L4466-L4482). It is not a documented bot/OAuth capability or proof of Discord approval. No account-backed profile request was performed during implementation.

The returned user, global metadata, member metadata, badges, connected-account labels, and mutual guild IDs follow the public [profile payload definitions](https://github.com/dolfies/discord.py-self/blob/master/discord/types/profile.py) and [profile parser](https://github.com/dolfies/discord.py-self/blob/master/discord/profile.py#L65-L104). Display/username/avatar, banner/accent color, bio/pronouns, badge descriptions, publicly returned connection labels/verification, mutual guild IDs/nicknames, and optional member nickname/avatar/banner/bio/pronouns/join date are rendered only when available. A null global metadata object is treated as unavailable; it is not proof that someone blocked the account. No premium status, relationship, shared activity, badge artwork, or connection URL is fabricated from missing fields. Unknown optional attributes are not retained.

Profiles are limited to 256 KiB of response bytes and 64 KiB of retained model data. Lists retain at most 16 badges, 16 connected accounts, and 50 mutual guild summaries; oversized lists visibly mark the profile as limited. Fields are copied into bounded strings. If the aggregate budget is reached, excess mutual guild summaries and badges are discarded first. Returned user and optional member guild identities are checked against the request. Oversized/unsupported profile responses fail within the card; authentication expiry/challenges still stop the session.

A dedicated cancellable task keeps the command loop responsive. REST uses four shared permits and server-controlled cooldowns; the cooldown mutex is released before network I/O so a slow profile body does not hold up an admitted message write. No automatic retry is added. The local HTTP test holds a profile response open while proving a message write can complete, and verifies route/query identity, the response limit, and mismatched-user rejection. Reducer and parser tests cover stale requests/sessions, cancellation, null metadata, guild identity, and maliciously large fields/lists. These are synthetic tests, not live interoperability evidence.

User and member banner/avatar CDN paths are **documented** in [Discord's image reference](https://docs.discord.com/developers/reference#image-formatting). Banners request static PNG at size 512; guild avatars request static PNG at size 128. Constructed keys accept only typed positive IDs and validated image hashes. The existing credential-free image worker and account image-cache limits apply; banners share the 512-pixel preview limit and 16 MiB texture LRU. Closing the card releases profile metadata; already fetched images remain in the ordinary bounded image cache until eviction, clear-cache, or logout. The demo generates original banner pixels without networking. Real profile/media delivery and Windows/Linux UI behavior remain unverified.
